# Scoping 03: Decision Log

*Started 2026-11-26 from the first review pass on the research and scoping docs.*

## Direction

| # | Decision | Why | Affects |
|---|---|---|---|
| D1 | **Concept C, *Nighthawk*** (derelict ship salvage), as described in Scoping 01 | Building the base and exploring the world are the same mechanic | Everything |
| D2 | **Rust** for the game | We want to learn Rust, safety helps avoid nasty bugs, and it's fast. Go + Bubble Tea + Wish isn't being pursued. | Tech stack |
| D3 | **Single-player only.** Multiplayer is dropped from the vision. | A better single-player simulation beats a multiplayer compromise. "Playing over SSH" means SSHing into your own machine and running the game in tmux, which needs no special support. | Non-goals, architecture |

## Simulation and design rules

| # | Decision | Why | Affects |
|---|---|---|---|
| D7 | **Time moves only when you act.** No real-time ticking anywhere, including environment systems. Every action has a time cost, and the world simulates exactly that much time. | You can leave the game sitting in tmux for days and nothing happens | Turn scheduler, all systems |
| D8 | **Fully 3D from the first line of code.** Positions are always (x, y, z). Decks are z-levels, and air, heat, fluids and creatures move between levels through shafts, hatches and breaches. | The 3D nature of DF and CDDA sets them apart (RimWorld's flatness is the biggest gripe) | Map, every grid system |
| D9 | **Tool qualities, not specific tools.** Recipes ask for `CUT 1`, `HAMMER 2`, and so on. | There should be a thousand ways to get `CUT 1` | Crafting, content |
| D10 | **Materials carry physical properties** (hardness, melting point, conductivity…) that drive tiers, damage, fire and construction. | DF's core lesson | Content model |
| D11 | **Inventory is physical containers with pockets**, like CDDA but with smoother UX. What you wear matters: a medical pouch on your belt survives dropping your backpack. | Containers make choices about what you carry, as in Project Zomboid | Items, UI |
| D12 | **Logistics is a problem the player solves, not one the game hides.** Early on you craft from what's on you and in containers within reach. Networked storage and item transport are machines you build later, in the style of Applied Energistics 2 and Mekanism. | Solving logistics is itself the fun | Crafting UI, automation, roadmap |
| D13 | **Automation must produce something that matters for survival or exploration**, such as ore-processing multipliers, O2 production or air scrubbing. It isn't automation for its own sake, which is the difference between Mekanism and Satisfactory. | — | Late-game design |
| D14 | **Life support is the needs model:** air, food, water, waste disposal, power, fatigue, radiation and lighting. MVP: O2, body heat, hunger, thirst and fatigue. Radiation and waste come right after the MVP. | All the systems people need, ONI-style | Body, base systems |
| D15 | **The stasis pod is a lifepod-style safety net.** It gives minimal emergency O2, heat and a basic fabricator, and it's your first respawn point. It's enough to scrape by on, not enough to thrive. | Subnautica's opening: scramble to survive while bootstrapping a real base | MVP opening |

## Technology

| # | Decision | Why | Affects |
|---|---|---|---|
| D16 | **Primary platform: Debian, inside tmux, over SSH from a macOS terminal (zsh).** Native macOS and Linux are expected to work. Windows is best-effort. | That's how the game will actually be played | Testing, input, colour |
| D17 | **Content is JSON**, validated in three ways: strict typed loading (`serde` with `deny_unknown_fields`, so a typo is a load error), a content-validation test (every reference resolves), and a **JSON Schema generated from the Rust types** (`schemars`) for editor autocompletion and checking. | Everyone knows JSON. RON has no schema advantage, and JSON's schema tooling is better. | Content pipeline |
| D18 | **The simulation stays separate from every UI.** Commands and events are plain serialisable data, so a future web front-end could stream state over WebSockets or HTTP, or run the sim in WASM. | Keeps the web option open | Architecture |
| D19 | **ECS choice deferred.** Plain structs until entity counts force a decision (bevy_ecs or hecs). | Simpler code while learning Rust; no lock-in | Architecture |

## Engineering practice

| # | Decision | Why | Affects |
|---|---|---|---|
| D20 | **Quality gates on every change** (`scripts/check.sh`): rustfmt; clippy with warnings as errors and complexity lints on; all tests; line coverage of at least 90% with cargo-llvm-cov; no function over cyclomatic complexity 10, measured by lizard. Unit tests are written alongside each piece of critical logic. | Catch bugs early, keep functions small enough to understand, and make sure the thing actually compiles | All code |
| D21 | **One set of instructions for people and agents.** `CONTRIBUTING.md` (rules and workflow), `TOOLING.md` (how to use each tool) and `AGENTS.md` (agent instructions; `CLAUDE.md` imports it rather than duplicating it). The Rust toolchain is pinned in `rust-toolchain.toml`, and the check script also builds the docs. | Anyone, human or agent, can build, test and contribute the same way with the same compiler | All contributors |
| D22 | **Determinism contract.** All randomness in the sim comes from `GameRng`: PCG32 (`rand_pcg`), one independent stream per game system, all derived from the world seed. We use only its raw output (pinned to the PCG reference values by a test) plus our own unbiased `below`/`one_in`/`pick`, never library helpers that may change between versions. `World::state_hash` (FNV-1a over explicit bytes) fingerprints the whole state. A golden test plays a fixed 500-command script and must match the stored hash; CI runs it on Linux and macOS, in debug and release. Stream numbers and tile hash IDs are never changed or reused. | Same seed + same moves = same game on every machine and version, which makes bugs reproducible and accidental changes visible | Sim, saves, CI |
| D23 | **Save and load come before more content (M0.4).** A save is the whole `World` as pretty JSON inside a `{format, version}` envelope; strict parsing (`deny_unknown_fields`), then consistency checks (map size, player position). Other versions are rejected with a clear message (no migrations before 1.0). One save slot, in the platform data folder (`~/.local/share/nighthawk/` on Linux, `~/Library/Application Support/nighthawk/` on macOS), overridable with `NIGHTHAWK_SAVE_DIR`. Binary saves come later, when saves get large. Golden tests save and reload mid-game and must still match the stored fingerprint. | Cheapest while state is small; every later system is built saveable; determinism turns save/load into a very strong test; JSON is readable while learning | Sim, TUI, all future state |
| D24 | **Title menu and leaving the game.** The game opens on a menu (New game / Continue / Quit; Continue is greyed out with no save). In a game, `q` saves and returns to the menu, `Q` returns without saving, `S` saves, Ctrl-C saves and exits; a failed save never leaves the game silently. `--seed N` skips the menu and starts that ship. A damaged save is reported on the menu, never blocking a new game. | Familiar flow; nothing is ever lost by accident; scripted runs and replays stay one command | TUI |
| D25 | **Decks and stairs.** Stairs come in pairs: stairs up ~~(`<`)~~ at a spot need stairs down ~~(`>`)~~ at the same x, y on the deck above (*glyphs and keys flipped by D31*), checked when a map or save loads. Climbing takes 2 turns; trying to climb without the right stairs takes none. Decks have optional names (shown as the map panel title; default "Deck N"). The starting map is now `aft_ring` ("Aft habitation ring": Stasis bay below, Crew quarters above). A content test requires every walkable tile to be reachable from the start, across decks. Save layout went to version 2; version-1 saves are rejected with a clear message. | Simple, predictable vertical movement that keeps the 3D promise (D8) and can't strand the player | Maps, sim, saves, content |
| D26 | **The browser build moves to M6, and M1 is done in six steps:** doors, air, breaches and vacuum, heat, field of view and lighting, then a soak test and performance budget (*moved to M5 by D51*). Map chunking waits until a map is big enough to need it. | Play is in tmux, so the browser can wait; the survival simulation is the game. Our decks are 32×14, so chunking would be complexity without benefit | Roadmap |
| D27 | **Doors.** `+` closed (blocks movement, and air from M1.2), `'` open. Walking into a closed door opens it: one turn, and you stay put. `c` plus a direction closes an open door beside you (one turn); you can't close the door you're standing in. Nothing-to-close costs no time. New tiles extend the save without changing its shape, so saves stay at version 2. Content reachability treats closed doors as passable. | The classic roguelike model: simple to learn, and the door is a real object air can't pass | Sim, TUI, content |
| D28 | **Air model.** Every air-holding tile (floor, ladders, open doors) stores O2, N2 and CO2 as partial pressures in whole pascals; the three are the whole mix, so their shares always total 100% (shown to 0.1% with largest-remainder rounding, so the display always adds to exactly 100.0). Normal ship air is 101,325 Pa: 21% O2, 78.96% N2, 0.04% CO2. ~~Each turn, every pair of connected tiles (four sides, and through ladders between decks; not diagonals) moves a tenth of their difference per gas, rounded to the nearest pascal, all computed from a snapshot so order never matters.~~ *Superseded by D30.* Walls and closed doors block air; a closing door traps its doorway's air until it opens. Air is never created or destroyed: a test plays the 500-command script and requires every gas total to stay exactly constant. Decks may set a starting `pressure` (0–200% of normal). Saves went to version 3. The air overlay (`a`) shades floor `█▓▒░.` by pressure; the sidebar shows the air where you stand. | Exact, deterministic and conserved by construction; the three gases are what later systems (breathing, scrubbers, fires) need. ~~Rounding leaves at most 4 Pa per gas per link of residual slope, a deliberate trade for exactness~~ | Sim, saves, content, TUI |
| D29 | **Units: a tile is 1 m, the clock counts seconds.** The world is simulated one second at a time, and each action takes a set number of seconds: a step 3 s, a diagonal step 4 s (about 1.4 m), climbing a ladder 20 s, opening or closing a door 2 s, waiting 5 s. Ambient sounds are about one per 25 s. The sidebar shows the clock as h:mm:ss. Save layout version 4 (`turn` became `seconds`). | Real units make every later system (breaches, breathing, power) easy to reason about and tune | Sim, saves, TUI, every future system |
| D30 | **Air evens out across each connected space every second** (replaces D28's spreading rule). At 1 m tiles and 1 s steps, pressure equalises at about the speed of sound, so within one second each connected open space (tiles joined through open floor, open doors and ladders) reaches one even pressure and mix. Each gas total is split evenly in whole pascals, leftovers one each to the first tiles in a fixed order, so it stays exact and deterministic. What will slow air down is the size of an opening, such as a small breach, not the room. | Physically right at this scale, cheaper to compute, and rooms read as single atmospheres on the overlay; the old tile-by-tile spreading was far too slow ("cold syrup") | Sim, M1.3 breaches |
| D31 | **`>` climbs up and `<` climbs down, and ladders are drawn the same way**: a ladder up is `>`, a ladder down is `<`, so you press the key you see. The starting map's file uses the same characters. (Flips the roguelike convention D25 followed, which felt reversed in play.) | Matches how the owner reads the symbols; drawing and key always agree | TUI, content |
| D32 | **The ship's calendar.** Every game begins at 08:42:00 on 25 November 2631; the date and time shown is that moment plus the seconds played. Gregorian calendar with its leap-year rule, computed with Hinnant's integer date algorithms (no dependency), tested day by day across 2500–2900. The sidebar shows `Date  25 Nov 2631` and `Time  08:42:00`. Saves are unchanged: they still store seconds. | Starting at a moment in the story rather than at zero; later systems (logs, shifts) can use real dates | Sim, TUI |
| D33 | **Hull breaches, vacuum and the breath meter.** Two hull-damage tiles, solid and airless: a crack (`x`, 4 cm²) and a breach (`X`, 400 cm²). Each second, every connected space loses the share of its air that streams out of the holes along its edge at choked flow (≈120 m/s × hole area) over its volume (each tile holds 2.5 m³: 1 m × 1 m × a 2.5 m deck), rounded up so a leak reaches vacuum. Air lost is counted (`Map::vented`): air on board plus air vented always equals the start, tested over the whole scripted game. A breach empties a small room in under a minute; a crack takes about 20. The player has a breath meter (0–100%): it refills in 20 s when oxygen is at least 14 kPa (about 3 km altitude) and drains by the shortfall otherwise (vacuum: about 36 s), with warnings at 75/50/25%. At 0% you black out: until there's a base to wake up in (D5), that ends the game back at the title without saving. The log says when air is escaping from your space. Save layout version 5. | Real physics in real units gives believable, tunable danger: closing a door in time saves you, leaving it open doesn't | Sim, content, TUI, saves |
| D34 | **Heat on every tile, and the warmth meter.** Each tile stores its air's *heat* as a whole number: pressure (Pa) × temperature (mK), so heat is only ever moved, never created or destroyed by rounding; temperature is heat ÷ pressure, and vacuum has none. Each second heat moves three ways: **with moving air** (tiles that lose air give up the same share of their heat; it goes to the tiles that gained air in proportion to their gain, and vented air takes its share to space); **between neighbouring air tiles**, 10% of the temperature difference per second weighted by both tiles' heat capacity (`pa·pb/(pa+pb)`), so cold creeps out of an opened room over minutes rather than the single second pressure takes; and **out through the outer hull** (the solid tiles on the map's border), about 1 °C an hour from a big room at room temperature, toward deep space at 3 K. Heat on board plus heat lost always equals the start, tested over the whole scripted game. Thermal mass is the air alone for now; the hull rate stands in for walls and insulation. Decks may set a starting `temperature` (−270 to 200 °C, default 20). The stasis bay starts at 14 °C and the crew quarters at −20 °C. The player has a **warmth meter** (0–100%): it recovers in air of 10 °C or more (empty to full in about 8 minutes) and otherwise drains by how far below 10 °C the air is (−20 °C: about an hour; −80 °C: about 20 minutes; vacuum counts as 0 °C), with warnings at 75/50/25%. At 0% you black out from the cold, which ends the game like running out of air (D33); the title says which. The heat overlay (`t`) shades floor by temperature: `░` green 10–30 °C, `▒` cyan 0–10, `▓` light blue −15–0, `█` blue below −15, `█` red 30 and up; `a` and `t` swap between overlays. The sidebar shows Warmth and Temp. Save layout version 6. | Pillar 2 needs cold as a gate you can see and plan around; storing heat rather than temperature keeps it exact and deterministic like the air, and heat that rides with air makes breaches and opened doors behave believably | Sim, content, TUI, saves |
| D35 | **Materials: every tile is a shape plus a material.** The shape (wall, floor, door, ladder, hull damage) decides behaviour; the material decides what it's made of, as in Dwarf Fortress. Materials are content in `data/materials.json` with real properties in SI units as whole numbers, CDDA-style: density (kg/m³), melting point (°C), specific heat (J/kg·K), thermal conductivity (W/m·K), Vickers hardness, a colour, a description, and the tool qualities that cut them (`"cut_by": { "LASER": 2 }`, levels 1–10, any one quality is enough, none means uncuttable). **Levels are set by hand** and tuned as the game grows, not derived from the physics. The file names a default material for every shape, so a map legend can stay `"#": "wall"` and only spell out exceptions as `{ "tile": "wall", "material": "nanocarbon_alloy" }`. The ship: steel floors, ladders and bulkheads (LASER 2), aluminium-alloy doors (LASER 1), and an outer hull of **Nanocarbon Alloy** (LASER 5). The world keeps its own copy of the materials, saved with the game, so editing the data file never changes a game in progress. Walls are drawn in their material's colour. **Look mode** (`V`): a cursor (movement keys; Esc, `V` or `q` to stop) shows the tile's shape, material, properties, LASER level, air and temperature, with the material's description in the bottom panel; no time passes. Materials don't change any physics yet. Save layout version 7. | DF's lesson that everything has a material, with CDDA's properties and qualities; hand-set levels are simpler to tune than physics-derived ones | Sim, content, TUI, saves, every later system |
| D36 | **The interact menu** (M1.6). `e` brings up the same cursor as look mode, starting on you; over a tile it lists what you can do there, each with its own key: `o` open, `c` close, `x` cut (none of them a movement key). Enter does the first action that can be done; Esc, `e`, `V` or `q` cancel. Each action has a reach, in steps with diagonals counting as one: opening or closing a door needs you right beside it, and you can't close a door you're standing in; cutting with a laser reaches **2 tiles** along a clear straight line (standing at (1, 1), you can cut a wall at (1, 3) across open floor at (1, 2)); a solid tile on the line blocks it. Anything solid can be cut if its material has a `cut_by` entry. Actions that can't be done stay listed, greyed, with a short reason (`too far: reach 1`, `path blocked`, `needs LASER 1`, `nothing cuts it`); choosing one logs the full reason, costs no time and keeps the cursor up. The rules live in the sim (`options_at`, `Command::Interact`), which checks them again before acting. Nothing can be carried yet, so cutting always needs a tool for now. Walking into a door still opens it, and `c` stays as a shortcut. | One way to inspect and one way to act, both by pointing; the reason an action is out of reach is always visible | TUI, sim commands |
| D37 | **Structures, and content in folders** (M1.7a). Every tile is a *structure* (what it is) made of a *material* (what it's made of). Structures are content in `data/structures/*.json`: id, name, description, glyph (and `open_glyph` for doors), a *behaviour* from a fixed list in code (`floor`, `wall`, `stairs_up`, `stairs_down`, `door`, `hull_crack`, `hull_breach`) and a default material. Data decides what exists and what it's called; code decides what a door does. A door's open or shut state belongs to the tile, not the structure. Map legends name structures (`"#": "bulkhead"`), optionally with another material or placed open (`{ "structure": "door", "open": true }`); `@` is an ordinary legend entry saying what the player starts on, and must be walkable. Materials move to `data/materials/*.json` and lose their per-shape defaults. Every content kind is a folder whose `.json` files are all loaded in name order, ids unique across the folder, errors naming folder and file. The world keeps its own copy of the structures, saved and hashed like the materials. The ship's structures: deck plating, ladders up and down, bulkhead (steel); hull plating, cracked hull and hull breach (Nanocarbon Alloy); door (Aluminium Alloy). Look mode names the structure, and bumping says what you hit ("the hull plating"). Save layout version 8. | The owner's split of "what it is" from "what it's made of", applied to the ship itself; folders keep content files small as content grows | Sim, content, TUI, saves |
| D38 | **Items, equipment and recipes: the plan for M1.7b–d.** Items are content in `data/items/*.json` (grouped by kind: `clothing.json`, `tools.json`, `salvage.json`); an item is an item type plus a material, and its mass is volume × density × how solid it is. Items you *wear* are equipment; items you *carry* go in the pockets of what you wear. You start wearing a jumpsuit (Cotton Fabric) with four 1 L pockets: left hip, right hip, left leg, right leg (2.5 kg each). A tool counts if it's anywhere in your pockets. Every change from one thing to another is a **recipe** in `data/recipes/*.json`: an action, what it acts on, what it uses, how long it takes, and what it becomes (the cutting level still comes from the material, D35). Planned recipes: cut a door (LASER 1 for aluminium, about 2 minutes) → damaged door, an open frame that can't be shut; patch a hull crack (1 scrap, about 1 minute) or breach (3 scrap, about 5 minutes) → hull plating made of the scrap's material; repair a damaged door (2 scrap, about 3 minutes) → door. A basic laser cutter (LASER 1) and 4 pieces of steel scrap lie in the stasis bay. | Makes the slice playable: a tool to find, a gate it opens, and leaks you can fix; recipes keep every transition in one data format that construction (M3) and crafting (M2) can reuse | Items, content, sim, TUI |
| D39 | **Items and the jumpsuit** (M1.7b). Item types are content in `data/items/*.json`: id, name, description, glyph, material, `volume_ml`, `solid_percent`, optional tool `qualities`, and optional `wear` with its pockets. An item in the game is a type, a material, and the contents of each of its pockets; its weight is volume × density × solid share ÷ 1000 g (100 ml of steel scrap: 785 g), plus its contents, and a pocket takes an item if both its volume and weight limits allow. | D40 | **Recipes, and cutting with a laser** (M1.7c). Recipes are content in `data/recipes/*.json`: id, action, `from` structure, `to` structure, seconds; one recipe per action per structure, checked on load, and the world keeps its own copy like the rest of the content. The first action is `cut`: the interact menu offers Cut only on something solid with a cut recipe (the hull's LASER 5 still shows in look mode). | D41 | **Agent tools.** `agent-tools/` holds helper scripts for AI agents, listed in `agent-tools/tool-descriptions.md`, Python 3 standard library only, with their own tests run by `scripts/check.sh`. The first two fix the most common agent mistake, an edit that misses because rustfmt reflowed the code: `show.py` formats a file before showing matches with line numbers, and `replace.py` applies OLD/NEW edit blocks all or nothing, matching while ignoring whitespace and rustfmt's trailing commas, refusing an OLD that matches nowhere or more than once and pointing at the closest text, then formatting again. | D42 | **Repairing with scrap** (M1.7d). A second recipe action, `repair` (key `r`, reach 1, not from the tile itself). | D43 | **Content is all data: Rust is a fixed set of building blocks** (the owner's choice of option 1 from a review of where Rust and JSON overlapped). Rust provides a small, fixed vocabulary: the *properties* a structure can have (as named fields, like `"walkable": true` or `"leak_cm2": 4`, not a CDDA-style flag list, so a misspelt field is a load error and fields can hold numbers), the *kinds of effect* an action can have (change a tile, pick up), the reasons an action can't be done, and the physics those properties drive. Everything specific (which structures, materials, items, qualities, actions and recipes exist, their names, keys, reaches, times and log lines) is JSON. An open door is its own structure, and opening and shutting are recipes like any other change. No scripting language. Replaces D37's "code decides what a door does" and the fixed lists in D35–D37; done in steps R1–R5 before M1.8. **R1 (done):** all content is one `Content` bundle (materials, structures, item types, recipes), loaded by `Content::load`, which asks the front-end to read each folder in `CONTENT_FOLDERS` and checks everything; the world keeps one copy; `Catalogue` and the per-kind parse functions are gone from the public API, so a new kind of content touches only the sim. Gameplay unchanged (the golden hash is the same). Agent tools: `replace.py --all` for renames, and `bless.py` to update a snapshot like the save-format test. Save layout version 12. | New verbs, tools and kinds of tile without Rust changes; one place to add a kind of content | Content, sim, TUI, saves, agent tools |
